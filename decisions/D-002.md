# Architectural Decision Record D-002: In-Memory Constraint Validation & State Machine Orchestration

## Status
Accepted

## Context
The system must enforce complex business constraints (e.g., BR-01 vehicle weight/volume limits and BR-02 driver shift limits) and manage state transitions across order batches and routes (`Draft` -> `Optimized` -> `Assigned` -> `In Transit` -> `Completed`). We needed to decide where to execute constraint validation and state rules.

## Decision
Implement constraint validation and state transition logic synchronously within the application core (Java service layer) using an explicit State Pattern/In-Memory Rule Engine before persisting state changes to the database[cite: 9, 12].

## Alternative Considered
Offloading constraint enforcement and state transitions to database triggers and stored procedures.

## Rationale
In-memory application-level validation ensures tight unit testing coverage, decoupling business rules from specific database engines, and providing instant inline failure feedback to dispatchers (`AC-02`)[cite: 9].

## Consequence Accepted
Slightly higher application server memory footprint during batch processing, and mandatory explicit locking during concurrent dispatch attempts (`AC-03`)[cite: 9].
