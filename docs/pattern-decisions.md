
# Design Pattern Decisions

| Design Problem in Our System | Selected Pattern/Technique | Participants | Justification |
|---|---|---|---|
| The route optimization algorithm may change as the system improves. The application should not need major changes whenever a different optimization method is introduced. | Strategy Pattern | `RouteOptimizationService`, `RouteOptimizationStrategy`, `NearestNeighbourStrategy`, `AlternativeOptimizationStrategy` | The Strategy Pattern encapsulates different route optimization algorithms behind a common interface. The service can use one strategy without depending on its concrete implementation. This supports the route-generation requirement FR-01 and makes algorithms easier to test and replace. |
| The system must send customer notifications without becoming tightly coupled to a particular SMS or WhatsApp provider. | Adapter Pattern (Ports and Adapters) | `NotificationService`, `NotificationPort`, `SMSAdapter`, `WhatsAppAdapter` | The Adapter Pattern allows different external messaging providers to implement a common interface. The core application calls `NotificationPort` instead of a provider-specific API. A new provider can be introduced with minimal changes to the core logic, supporting FR-06 and the Phase 1 modifiability quality scenario. |
| Dispatching, tracking, and route optimization must communicate without directly depending on each other's internal implementations. | Dependency Inversion Principle (DIP) with interface-based service boundaries | `DispatchService`, `RouteOptimizationPort`, `RouteRepository`, `NotificationPort` | High-level business logic depends on stable interfaces rather than concrete database, algorithm, or messaging implementations. This reduces coupling and allows individual components to be tested using substitutes or mocks. It also supports the project's modular-monolith architecture. |
